# Salutant Decision Log

The project choices, their limits, and the decisions still open.

When a choice changes, a later entry names what it replaces. The earlier entry stays as history. The [Evidence Record](evidence-record.md) tracks the checks.

## How this log works

Each entry states the choice, its effect, and its status. Decision evidence stays private; this public log records only what the project needs. The private Playbook holds the Charter and Roadmap. [Requirements](requirements.md) owns the sign-in contract and open technical choices.

A proof is the signed message that says an address was checked. The epoch is a number only the owner can raise after a restore to reopen the service.

## Settled choices

- **S1 Free is required** Effect: no paid plan or feature. A free limit stops the service and never bills. Status: Settled.
- **S2 Hosting order** Salutant hosts on GitHub when possible, then Cloudflare, then Vercel. Status: Settled.
- **S3 Build our own email sign-in** Effect: Salutant exists. The six-digit format was a recommendation, not the owner's words, until S29 settled it. Status: Settled for the idea; format settled by S29.
- **S4 Separate repo** Salutant has its own repo. Status: Settled.
- **S5 Documentation-only merges** Effect: documentation-only merges are allowed in this repo, not code, tests, CI, or releases. Status: Settled, scope documentation only.
- **S6 Plan template** Effect: Salutant's plan uses the standard template. Status: Settled.
- **S7 Replace the repo's contents** Effect: the repo's old contents go, and their history stays in git. At that time nothing changed until the build go-ahead. Status: Settled; the Phase 1 go-ahead was later given (see S12).
- **S11 Phase 1 plan adopted** Effect: the Phase 1 plan is adopted for Phase 1 only: code on a branch in the salutant repo, using fakes. It allows no accounts, no domain setup, no real emails and no launch. Adopting the plan is not the go-ahead to write code. Status: Settled.
- **S12 Phase 1 code started** Effect: local and mock work (mock means tests use stand-in services instead of real ones) started on a branch with a pull request, and nothing merges without the owner. It does not cover accounts, real mail, cloud tests, connecting an app, merge, release, or later phases. Status: Settled.
- **S13 Browser binding kept** Effect: each sign-in challenge stays bound to the browser that asked (browser binding), in the Phase 1 design. A random value held in that browser does the binding, and the emailed code works only when entered there. An intercepted email alone cannot complete the sign-in. The cost: a code entered on another device fails. This is a design choice only. It covers no merge, account, real mail, cloud work, or later phase. The original spec wording on browser binding was aligned with this entry after the decision, and this entry governs the decision status. This log adopts no other unresolved spec value. Status: Settled.
- **S14 Phase 1 pull request merged** Effect: the Phase 1 local and mock pull request (pull request 59) was merged to main at its reviewed head. Scope: Phase 1 local and mock code only. Accounts, real mail, cloud work, deployment, connecting an app, release and any later phase are not covered; each still needs its own authorization. Status: Done.
- **S16 Who can sign in** Effect: only an approved list can sign in. It starts with the owner's address, and people are added only on the owner's say-so. Status: Settled.
- **S17 One app or many** Effect: one service that can serve many apps; a first app is connected first. Status: Settled.
- **S18 Where the code page lives** Effect: the code-entry page is on Cloudflare; public pages are on GitHub Pages. The claim that GitHub Pages cannot block framing was a statement in the question and is supported only by sampled-header evidence. Status: Settled.
- **S19 Lost mailbox** Effect: no shortcut in the sign-in; the owner fixes it by changing the approved address in the service settings, using the owner's own account access. Status: Settled.
- **S20 Runtime and storage** Effect: a Cloudflare Worker (a small program that Cloudflare runs for us) with its built-in free storage for codes and limits; the restore safety switch (the epoch) is a separate setting only the owner can change. How the owner sets the epoch, and how quickly every running copy receives it, remain Open. Status: Settled; epoch mechanism Open.
- **S21 Trial recipients** Effect: trial emails go only to the owner's own address. Status: Settled.
- **S22 Lockout residual** Effect: someone who knows the owner's address can delay the owner for up to an hour at a time. This is a known limit for the owner-only trial; a bot check is added before Salutant opens to anyone else. The up-to-an-hour delay is replaced by S33; the bot-check condition stands. Status: Settled.
- **S23 Playbook** Effect: the Playbook became Salutant's one plan, originally with Charter, Roadmap, and How It Works. The older drafts were deleted. The October 11 documentation decision moved technical behavior to the repo; the Playbook now holds Charter and Roadmap. Status: Settled.

- **S27 Mail path, current** Effect: sign-in mail goes through Resend from mail.soliskit.com, replacing the earlier dedicated Gmail account; iCloud stays dropped. Account creation, domain setup, credentials, and real sends remain later-phase work, each authorized separately. The mail adapter stays independent of any one mail provider. Provider limits and delivery remain to be checked before real sends. Status: Settled for the mail path; real sending unproven.

- **S28 Emergency revoke window** Effect: after an emergency signing-key revoke (removing a signing key at once because it may be compromised), apps stop trusting the old key within at most 10 minutes. This is a hard maximum for the owner-only trial, on the condition that cloud tests prove it. This sets the safety limit only; it is not a go-live, and it settles the open Playbook item on emergency key staleness. Status: Settled as a limit; cloud proof pending.
- **S29 Six-digit code format** Effect: the sign-in code is six digits, with limits on wrong guesses. This settles the code format left open in S3 and adopts the recommendation for it. Format only; it covers no real emails and no go-live. Status: Settled.
- **S30 Code lifetime** Effect: a sign-in code expires after 30 minutes, works once and only in the browser that asked for it. Lifetime value only; this replaces the proposed 10 minute value. Status: Settled.
- **S31 Wrong-guess limit** Effect: five wrong guesses cancel a sign-in code; signing in then needs a new code. Per-code limit only. Status: Settled.
- **S32 Resend wait** Effect: a resend can be asked for only after a one-minute wait; a resend replaces the old code for that attempt. Wait only. Status: Settled.
- **S33 Two unfinished attempts** Effect: at most two unfinished sign-in attempts for the owner's address at once. A slot frees when its code is used, cancelled by five wrong guesses, or expires. An outsider who fills both slots can delay the owner by up to 30 minutes. This is a known limit for the owner-only trial, and it replaces the up-to-an-hour delay in S22. Status: Settled.
- **S34 Three emails per 30 minutes** Effect: at most three sign-in emails to one address per 30 minutes, including resends; once used up, the address waits for the window to reset. An outsider can use up the allowance and delay the owner. This is a known limit for the owner-only trial. This entry claims no provider quota. Status: Settled.
- **S35 Ninety percent of the free mail allowance** Effect: sign-in mail uses at most 90% of the mail provider's current free allowance (current provider amounts and the check date live in E5 of the [Evidence Record](evidence-record.md#platform-notes-and-their-evidence-limits)); the service stops rather than pays. Other mail on the same account reduces the allowance. The three-per-address limit in S34 stays. Policy only; no account and no real mail is authorized. Status: Settled.
- **S36 Ten requests per hour** Effect: at most 10 sign-in requests per hour for one email address and 10 per hour for one internet address; extra requests wait until the window resets. This limit is separate from the email-send allowance in S35. A shared internet address can block a real retry. This is a known limit for the owner-only trial, to revisit before opening to others. Policy only. Status: Settled.
- **S37 Five-minute proof** Effect: the one-time sign-in proof expires after five minutes and works once; an expired proof does not sign the owner out, and the app manages the session separately. Allowing for small clock differences stays a separate proposal. Status: Settled.
- **S38 One-minute clock tolerance** Effect: a one-minute clock difference is allowed when checking the five-minute proof, so a proof may be accepted up to one minute past expiry, about six minutes in total. This does not change the email code lifetime (S30) or the key-revoke limit (S28). It settles the clock-difference allowance left as a proposal in S37. Status: Settled.
- **S40 Three wrong guesses** Effect: three wrong guesses cancel a sign-in code; signing in then needs a new code. Per-code limit only. This replaces the five in S31 and the five mentioned in S33; both entries stay as history. Derivation: with six digits (S29), three guesses give an attacker about a 1-in-333,000 chance per challenge, codes expire in 30 minutes (S30), and during the owner-only trial codes reach only the owner's mailbox, so the tighter limit costs the owner little. Locked October 15, 2026. Status: Settled.
- **S39 Record keeping** Effect: expired sign-in attempts and address-linked limits are deleted within 24 hours; the service's own basic event logs are kept 14 days; logs never contain email addresses, codes, or proofs. This covers the service's own records only, not the mail provider's copy or cloud backups; provider retention lives in E5 of the Evidence Record. Single-use protection that is still needed is not removed early. Status: Settled.

## Derivation decisions (October 15, 2026)

On October 15 the owner reviewed each picked number behind the settled choices, one at a time, with its derivation and options. Each entry records the value confirmed, the derivation as presented at the time, and the lock. Notes marked "author's analysis" were added afterward for the record and were not part of the presented questions. The wrong-guess limit was tightened from five to three in the same review; that change is recorded with its own amendment entry.

- **Code format (S29)** Six digits. Derivation as presented: with five guesses per code, one challenge gives an attacker about a 1-in-200,000 chance; codes expire in 30 minutes (S30), and longer codes tax the owner on every challenge. Options: six digits, eight digits, six letters-and-numbers. Locked: six digits. Author's analysis (added afterward, not part of the presented question): during the owner-only trial codes reach only the owner's mailbox, and browser binding blocks cross-challenge use (S13). Later note: the wrong-guess limit was tightened to three afterward (see the amendment entry), which improves the same odds to about 1 in 333,000; the conclusion is unchanged.
- **Abuse defenses (S32, S33, S34, S36)** Confirmed as recorded: a one-minute resend wait, two unfinished attempts per address, three emails per address per 30 minutes, and ten requests per hour per email address and per internet address. Derivation: during the owner-only trial these bound nuisance and lockout, not break-in risk, since codes reach only the owner's mailbox. Locked: all four. Author's analysis (added afterward, not part of the presented question): the resend wait is longer than normal mail delivery and resends are already capped by the send budget; two slots is the minimum that leaves the owner a working slot while one is held, and the worst delay is one code lifetime; three sends matches the real pattern of send, resend, and one spare while bounding budget burn; ten per hour is about three times the legitimate hourly need and the lowest round number that keeps the owner reachable behind a shared internet address. The same review tightened the wrong-guess limit, recorded in its amendment.
- **Key-revoke window (S28)** Ten minutes, derived as the five-minute app key cache plus the five-minute endpoint cache - the two layers a public key passes through. Locked: both caches adopted at five minutes as production settings; the settled hard maximum stands.
- **Proof timing (S37, S38)** A five-minute proof with a one-minute clock tolerance, a six-minute outer window. Derivation as presented: replay is stopped by single-use redemption, not expiry, so the window is hygiene rather than the security mechanism. Locked. Author's analysis (added afterward): five minutes covers slow redirects and the app's own shorter exchange window, and one minute covers realistic clock drift.
- **Mail allowance (S35)** Ninety percent of the mail provider's free allowance. Derivation as presented: the free allowance is 100 emails per day and 3,000 per month, counting both sent and received; 90 percent is the pick, the 10 percent headroom keeps the account's other mail from starving, and overshoot would mean silent mail failure elsewhere. Locked. Author's analysis (added afterward, not part of the presented question): the rule - stop rather than pay, re-read each milestone - is derived while the 90 is the pick; the headroom also absorbs quota-counting quirks (multiple recipients count separately - E5 of the Evidence Record).
- **Record keeping (S39)** Expired attempts and address-linked state deleted within 24 hours; service logs kept 14 days. Derivation as presented: the code already purges challenges one hour after expiry; 24 hours is the shortest deadline that survives a missed purge run - the shortest defensible deadline for the address-linked data; logs hold no addresses or codes, so 14 days is cheap incident history. Locked. Author's analysis (added afterward, not part of the presented question): the hashes serve single-use and limit enforcement only until code expiry plus margin, and the logs hold no proofs either (S39).
- **Cross-project retention** Salutant's retention numbers stay divergent from Pinto's month. Derivation: the talkable number is per service because the data classes differ - Pinto keeps user-submitted content the owner reads, while Salutant keeps only operational hashes and bare event logs, so its numbers are the shortest defensible ones. Locked.
